# R13 — 직렬 개발 큰 그림과 Git 운영

2026-09-26. T15a–g는 기존 흐름대로 수행한다. 그 이후 기능적으로 다른 작업은 독립 숫자로 나누었다. T16–40은 실행 명세이며 아직 구현한 것이 아니다. 총 task 수를 24개 또는 40개로 제한하지 않는다.

## 먼저 도달할 제품

1. T15 종료: 12개 부위를 탐색하고 현재 확보된 장면에서 근육과 뼈 각각의 설명을 읽는다.
2. T18 종료: 사람이 대신 표를 작성하지 않아도 종아리 기본 자료가 출처 대조표와 함께 준비된다.
3. T25 종료: 한 종아리 근육에서 설명과 실제 교육용 움직임을 연결한다.
4. T29–31 종료: 소흉근 선택→주변 흐림→작용 설명→움직임 선택을 완성하고 첫 로컬 학습판으로 검증한다.
5. 이후: 이 구현 패턴으로 전신의 구조·기능·움직임을 늘리고 평가 학습을 연결한다.

전신 모든 부착 표면과 사람 검토가 끝날 때까지 작용 학습 개발을 기다리지 않는다. 구조→기능→평가라는 학습 논리는 유지하면서 대표 부위에서 전체 흐름을 먼저 검증한다. 정확한 표면이 없는 항목은 텍스트 설명/관련 뼈로 제공한다.

## T15 흐름 — 번호와 범위 유지

T15a 이름 → T15b 계약(Sol High) → T15c 12부위 UI → T15d 뼈 카드 → T15e 장면 로더(Sol High) → T15f 종아리 통합 → T15g 전신 목록·자산 배치 계획. T15b/T15e는 미래 animation과 호환되는 안정 ID/frame/lifecycle을 보존하지만 이번에 움직임을 구현하지 않는다. T15g는 inventory·계획 작업으로 끝내고 새로운 자료 배치의 실행은 이후 숫자 task로 넘긴다.

현재 실제 진도는 work/STATUS.md와 해당 보고서를 확인한다. 문서에 예전 next task가 있어도 완료된 T15a를 자동 재실행하지 않는다.

## 더 필요한 task를 추가하는 방법

work/task-registry-r13.json에서 다음 미사용 정수 번호를 확인한다. 예를 들어 T28에서 견갑골 시범 하나를 검증했고 나머지 두 개가 별도 작업이라면 T41, T42를 발급하고 T28→T41→T42→T29로 명시한다. T28a/b/c를 끝없이 붙이지 않는다. 이미 끝난 번호를 바꾸거나 기존 보고서의 의미를 바꾸지 않는다.

등록할 때 반드시 대상 ID·범위·모델·선행·산출물·합격 기준·다음 작업을 작성한다. 한 자료 task는 최대10개 개념/관계, 자산 task는 한 장면 또는 한 clip이 기본이다. 숫자 순서만으로 의존성을 추측하지 않도록 queueOverrides와 STATUS의 NEXT_TASK를 함께 갱신한다. 새 task는 현재 작업 결과를 보고 등록하며 자동 실행하지 않는다.

## 언제 커밋하는가

- **지금의 누적 변경:** T15a를 수행한 task가 검증/커밋을 끝낸 뒤, T15b 시작 전에 기존 T13c–T14 및 설계 변경을 한 번의 로컬 체크포인트로 정리하는 것을 권장한다. 다른 task가 같은 checkout에 쓰는 동안 커밋하지 않는다. 이미 T15a 커밋이 생겼다면 그것을 되돌리거나 다시 쪼개지 않는다.
- **앞으로:** 한 task의 관련 검증과 보고서를 마치면 그 task의 변경을 로컬 커밋한다. T15a–g 각각도 이 원칙을 따른다. 더 큰 완성을 기다리며 수일간 변경을 누적하지 않는다.
- **미완 작업:** 테스트 실패/자료 부족이 있는 상태도 사용자 지시가 있거나 해당 task가 허용한 checkpoint라면 실제 상태를 드러내는 WIP/checkpoint 메시지로 저장할 수 있다. 커밋했다고 완료 상태를 올리지 않는다.
- **통합 시점:** T15f, T25, T31, T40에서는 통합 검증 기록을 포함한 커밋을 추가한다. 과거 task 커밋을 억지 재분할하거나 rebase하지 않는다.
- **push:** 로컬 커밋은 이 컴퓨터의 기록이다. 원격 백업은 별도이며 현재는 push와 배포를 하지 않는다. 사용자가 원격 저장소와 push를 명시하면 공개 범위·비밀·라이선스·큰 자산을 확인한 뒤 진행한다. push가 배포를 유발하는지 CI 설정도 확인한다.

포함: 코드, schema, 필수 학습 데이터, lockfile, 설계/보고서, 재현에 필요한 작은 검증 결과. 파생 GLB는 앱 실행에 필요하고 재배포가 허용되며 크기가 적절한 경우 포함한다. 큰 자산은 무조건 Git에서 빼기만 하지 않고 외부 보관/LFS/재생성 방법 중 실제 사용할 경로를 정해 manifest/hash와 함께 남긴다. 해당 도구를 자동 설치하거나 원격 업로드하지 않는다.

제외: OpenSim_Models 원본, 비공개 수업 원문/private-sources, 비밀정보, node_modules/dist/cache, 불필요한 동영상·중복 스크린샷·before 백업. 필수 검증 기록은 작게 선별한다. 기존 ignored 파일이 있다는 이유만으로 안전하다고 단정하지 않고 staged diff를 직접 확인한다.

선택한 파일/부분만 stage→staged diff와 검증 결과 확인→로컬 commit→HEAD/잔여 status 보고 순서다. task의 새 파일을 commit해도 같은 기능의 기존 미커밋 의존 파일이 빠지면 재현 불가하므로, 그런 경우 checkpoint 범위를 별도로 정하거나 commit 불가 사유를 보고한다. git add .로 모든 변경을 끌어넣지 않는다.

## 누적 체크포인트용 프롬프트

```text
다른 작업이 이 checkout에 쓰고 있지 않은지 확인한 뒤 로컬 Git 체크포인트만 만들어라.
최신 HEAD 이후의 T13c–T15 및 R12/R13 설계 변경을 검토하고,
실행에 필요한 코드·데이터·설계·작업 보고서·필수 검증 기록을 선별해라.
이번 체크포인트에 필요한 기존 미커밋 변경을 포함해도 된다.
기존 변경을 삭제·되돌리지 말고 OpenSim_Models·비공개·비밀·임시·불필요 대용량은 제외해라.
최신 관련 검증과 staged diff를 확인하고 실제 완료/미완을 드러내는 메시지로 로컬 커밋해라.
기존 커밋을 재작성하거나 과거 task별로 억지 분할하지 마라.
해시·포함·제외·남은 변경을 보고하고 멈춰라. push·배포·다음 구현은 하지 마라.
```
