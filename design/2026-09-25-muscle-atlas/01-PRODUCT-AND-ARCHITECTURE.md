# 제품과 구조 설계

## 1. 사용자 경험

첫 화면은 참고 이미지처럼 밝은 배경, 중앙의 큰 3D 모델, 좌측 탐색, 우측 설명을 사용한다. 피부·혈관·장기를 한꺼번에 싣지 않고 학습 중인 근육과 그 부착 구조를 우선 표시한다. 이미지의 메시 개수는 제품의 완성도를 뜻하지 않는다.

```text
┌ 전체 검색: 한글·한자·영어 ─── 표시 언어 ─── 학습 / 검토 ┐
│ 부위 / 근육 목록 │          3D 화면           │ 선택 근육 │
│ 좌 / 우 / 중앙  │ 회전·확대·정면/후면/측면    │ 세 언어명 │
│ 표층 / 심층     │ 선택·격리·주변 투명화       │ 구조      │
│ 뼈·근육 표시    │ 기시 O / 정지 I / 근두 선택 │ 기능      │
│ 미지원 포함     │ 부착면 확대·원래 보기 복원  │ 평가      │
│                │                            │ 출처 펼침 │
└ 학습할 근육 이동 ─── 현재 위치·좌우·층 ─── 복습 ─────────┘
```

데스크톱에서는 좌측 260px 안팎, 우측 360–420px를 시작값으로 삼고 화면에 맞춰 조정한다. 태블릿에서는 한쪽 패널만 펼치고, 모바일에서는 3D와 설명을 전환한다. 3D를 다룰 수 없는 기기에서도 텍스트와 출처·근육 목록은 이용할 수 있어야 한다.

근육을 선택하면 이름은 한글·한자·영어로 함께 표시한다. 설정으로 주 언어만 바꿀 수 있고, 세 언어 검색은 항상 가능하다. 용어가 미확인이라면 해당 칸에 “확인 중”을 표시한다. 사용자가 외우기 좋은 한글 표준명/관용명 조합을 제공하되 검증되지 않은 명칭을 표준으로 선언하지 않는다.

## 2. 구조 화면: 이름보다 부착 관계가 중심

각 근육의 구조 화면은 다음 순서로 읽는다.

1. **어디에 있는가:** 부위, 좌우, 표층/심층, 인접 근육.
2. **무엇에 붙는가:** 기시·정지의 구체적인 뼈 표지 또는 근막·건·피부 등 구조.
3. **어떤 경로로 이어지는가:** 근복·근두·건, 지나는 관절, 구조 간 관계.
4. **왜 기능을 이해하는 데 중요한가:** 기능 화면으로 연결하는 짧은 구조적 단서. 실제 설명은 출처 있는 기능 데이터가 생겼을 때만 표시.
5. **얼마나 확인되었는가:** 텍스트와 3D 좌표 각각의 검토 상태와 근거.

지배신경과 분절 정보도 구조 데이터에 포함한다. 신경 자체의 3D 메시가 없어도 출처 있는 텍스트 관계부터 담을 수 있다. 평가 단계에서 근육 자체의 문제와 신경계 원인을 함께 사고할 수 있게 하기 위한 연결이다. 분절 표기가 출처마다 다르면 차이를 보존하며 특정 신경근 병변을 자동 추론하지 않는다.

기시와 정지는 점 하나만 찍는 방식으로 고정하지 않는다. 좁은 부착은 점, 긴 부착은 선, 넓은 부착은 면으로 표시한다. 위치를 대표하는 마커와 실제 부착 범위는 구분한다. 청록색 O, 황색 I처럼 색과 문자·윤곽을 함께 사용하여 색각에 의존하지 않는다. 기시/정지 문장을 누르면 해당 표지를 확대하고, 3D 표지를 누르면 그 문장으로 이동한다.

근두가 여러 개인 근육은 전체 선택과 근두 선택을 모두 지원한다. 넓은 근육, 여러 손가락으로 향하는 건, 근막·피부에 닿는 구조, 고유한 기시/정지 구분이 어려운 근육도 모델에 넣을 수 있어야 한다. 모든 근육을 “뼈 하나의 점 A → 뼈 하나의 점 B”로 제한하면 전신 확장 단계에서 다시 설계해야 한다.

깊은 근육은 주변 근육 투명화/숨김으로 관찰한다. 숨긴 구조는 목록에서도 표시하고, 항상 “모두 복원”을 제공한다. 투명한 표면이 클릭을 가로막지 않도록 선택 규칙을 명시한다. 라벨은 화면을 덮지 않도록 선택 항목 위주로 표시하고 뒤에 가려진 구조는 점선 또는 별도 표식으로 구분한다.

## 3. ‘모든 근육’의 분모

대상은 **성인 사람의 골격근**이다. 심근·평활근은 기본 범위 밖이다. 팔다리만 완성하고 전신이라고 부르지 않는다. 목록은 머리·얼굴·저작·눈·혀·인두·후두·목·등·흉곽/호흡·복벽·골반저/회음·어깨/상지·손·엉덩이/하지·발을 포함하도록 점검한다. 성별 특이 구조는 적용 범위를 기록한다.

TA2 같은 표준 목록을 기준 후보로 삼고, 사용 가능한 판본을 확보한 뒤 전신 대상 목록을 동결한다. 한국어·한자는 별도 한국어 출처로 연결한다. 표준 목록은 이름의 기준이지 기시·정지·검사법 전체의 출처가 아니다.

- 근육 개념 하나와 좌우 인스턴스를 구분한다.
- 근두·부분은 상위 근육에 연결하되 목록에서 독립적으로 펼칠 수 있다.
- 근군/집합, 개별 근육, 근두, 모델의 힘줄/액추에이터를 다른 유형으로 둔다.
- 해부학적 변이는 기본 근육과 별도 분류하고 존재 빈도를 임의 입력하지 않는다.
- 정중 구조를 강제로 좌우 복제하지 않는다.
- 전체 목록에서 의도적으로 제외한 항목도 이유를 보존한다.

진행률은 `명칭 검토`, `기시·정지 텍스트 검토`, `3D 형태`, `부착 영역 검토`, `기능`, `평가`로 나누고 각각 분모를 보여 준다. 개념 수, 좌우 인스턴스 수, 근두 수, 메시 수를 섞지 않는다. 미지원 구조를 검색에서 숨기면 누락을 발견할 수 없으므로 검색에는 남긴다.

## 4. 세 종류의 자료를 분리

| 자료 | 역할 | 대신할 수 없는 것 |
|---|---|---|
| 해부학·검사 문헌 | 이름, 부착, 기능, 평가 설명의 근거 | 해당 3D 메시의 좌표 정확도 |
| 3D 형태 데이터 | 근육·뼈의 형태와 공간 배치 | 전체 근육 목록, 검증된 부착 영역 |
| OpenSim | 모델에 정의된 근육 경로·관절·운동 계산 | 전신 근육의 입체 근복, 임상 검사 타당도 |

현재 로컬에서 `.osim` 34개와 공용 Geometry 파일 325개를 확인했다. `Rajagopal2016.osim`의 실제 ForceSet 안에는 근육 액추에이터 80개가 있다. XML의 기본값 템플릿까지 세면 81개가 나오므로 기본값은 제외했다. 이것을 해부학적 근육 80종 또는 전신 완성으로 해석하면 안 된다.

**권고:** 구조 단계에서 BodyParts3D를 3D 형태 후보로 시험하고, 통과하면 부위별로 사용한다. 데이터 자체의 누락·형태 오류 가능성과 판본별 좌표 차이가 공지되어 있으므로 이름이 맞는 파일을 찾았다는 것만으로 통과시키지 않는다. 다른 공급원의 메시를 혼합할 때는 등록/정합 검증이 필요하다. [BodyParts3D 공식 안내](https://lifesciencedb.jp/bp3d/info_en/index.html)

OpenSim은 별도 adapter와 “모델 경로 보기”로 보존한다. 경로를 굵은 튜브로 그려 근육 형태가 완성된 것처럼 보이지 않게 한다. 원점·축·크기만 맞춘다고 다른 인체 모델의 부착 좌표가 해부학적으로 일치하는 것은 아니다. [OpenSim 공식 입문](https://opensimconfluence.atlassian.net/wiki/spaces/OpenSim/pages/53088700)

## 5. 기능 단계

기능은 근육당 동사 목록이 아니라 조건 있는 관계다.

| 요소 | 담을 내용 |
|---|---|
| 기본 작용 | 어느 관절에서 어떤 움직임에 기여하는가 |
| 자세 조건 | 관련 관절의 자세, 인접 관절 고정 여부 |
| 수축 역할 | 단축성 움직임, 신장성 제어, 등척성 유지 |
| 안정화 | 어떤 과제에서 어떤 구조를 안정시키는가 |
| 협력 관계 | 주동·협력·길항 관계와 적용 조건 |
| 다관절성 | 다른 관절 위치에 따라 길이·작용을 해석하는 단서 |
| 근거 | 설명의 출처와 해석 부분 |

동일 근육도 과제에 따라 역할이 달라질 수 있으므로 “항상 주동근” 같은 전역 속성을 두지 않는다. 움직임 화살표는 교육적 방향 표시이고 힘·활성·진단 확률을 뜻하지 않는다. 정량 모멘트암이나 힘을 표시하려면 모델, 자세, 단위, 계산 방법, 검증 범위를 별도로 제시해야 한다.

첫 기능 릴리스는 텍스트와 검증된 포즈/화살표만 제공한다. 실제 근육 변형 애니메이션, 역동역학, EMG 추정, 환자 맞춤 생체역학은 후순위다. 보기 좋은 애니메이션이 기능 설명의 정확성을 대신하지 않는다.

## 6. 평가 단계: 구조 → 가설 → 검사 → 해석

근육 페이지에서 그 근육의 평가를 볼 수 있고, 움직임 페이지에서는 같은 과제에 관련된 여러 근육을 비교할 수 있게 한다. 한 검사와 한 근육은 일대일 관계가 아니다.

학습 흐름은 다음과 같다.

1. **호소/관찰:** 어떤 동작, 부하, 범위, 시간 경과에서 불편한가.
2. **구조 후보:** 근육·건 외 관절, 신경 등 함께 살펴볼 구조는 무엇인가.
3. **기능 가설:** 힘 생성 저하, 통증으로 인한 수행 저하, 가동 범위 제한, 지구력 저하, 운동 조절 변화 중 무엇을 확인하려는가.
4. **검사 선택:** 능동/수동 움직임, 저항, 근력·지구력, 길이, 과제 관찰 등을 목적에 따라 선택.
5. **실행:** 자세, 고정 부위, 움직임, 저항 위치·방향, 관찰 항목, 중단 조건.
6. **해석:** 관찰된 사실과 가능한 해석을 분리하고 혼란요인·대체 원인을 확인.
7. **다음 확인:** 추가로 비교할 움직임/검사 또는 평가를 중단하고 의학적 확인이 필요한 조건.

각 검사 카드에는 `목적 → 관련 구조 → 시행 → 관찰 → 해석 범위 → 한계 → 다음 확인`을 적는다. MMT만으로 기능이상 평가를 완성했다고 하지 않는다. 모든 작은 심부 근육에 독립적인 수기 근력검사가 있다고 가정하지 않는다. 독립 평가가 어렵다면 근군/동작 수준에서만 평가 가능하다고 표시한다.

예를 들어 “발뒤꿈치 들기 과제”를 만들 때는 실제 과제 수행, 통증, 반복 수, 보상, 관절 위치를 기록하는 설계가 필요하다. 과제 실패를 곧바로 특정 근육 병변으로 변환하는 규칙은 만들지 않는다. 이것은 평가 카드의 설계 예시이며, 검사 프로토콜의 구체적인 자세·반복 수·정상 기준은 해당 근거를 확보한 뒤 입력한다. 수기 근력 평가에서 저항과 좌우 비교를 사용하는 기본 접근은 [Merck Manual](https://www.merckmanuals.com/professional/neurologic-disorders/neurologic-examination/how-to-assess-muscle-strength)을 참고할 수 있다.

위험 신호와 검사 중단 조건도 근거가 있는 교육 콘텐츠로 관리한다. 정상 수치, 민감도/특이도는 연구 대상·검사 변형·기준검사·출처를 함께 기록한다. 출처가 없으면 숫자를 생성하지 않는다. 환자 기록 저장·자동 진단·치료 추천은 이번 앱에서 구현하지 않는다.

## 7. 기술 구조

```text
원본 자료(읽기 전용) → 수집/변환 → 검토 대기 JSON
                                      ↓ 검증·리뷰
                               버전 고정 학습 데이터
                                      ↓
React UI ← domain selectors → 지식 관계/검색 인덱스
   ↕ stable IDs
Three.js viewer ← mesh manifest + attachment overlays
                       ↑
              별도 OpenSim adapter (후순위)
```

초기에는 서버·로그인·LLM API·벡터DB 없이 정적 웹앱으로 충분하다. Vite/React/TypeScript로 UI, Three.js로 3D를 만들고 공개 에셋 전달 형식은 GLB/glTF를 기본으로 한다. [Three.js 문서](https://threejs.org/docs/), [Khronos glTF](https://www.khronos.org/gltf/)가 구현 기준이다. 패키지 버전은 첫 구현에서 호환 조합을 선택하고 lockfile로 고정한다. 현재 설계 문서에 가상의 최신 버전을 박아 두지 않는다.

```text
HUMAN ATLAS/
  OpenSim_Models/                 # 기존 원본: 수정 금지
  design/2026-09-25-muscle-atlas/  # 이번 설계
  atlas-web/
    src/domain/                  # 타입, ID, 관계, 필터
    src/features/{atlas,search,structure,function,assessment,review}/
    src/viewer/                  # 3D 선택, 카메라, 레이어, 오버레이
    public/assets/               # 공개 가능 여부 확인한 파생 에셋만
    scripts/                     # 변환·검증·인덱싱
    tests/                       # 의미 있는 실패·브라우저 테스트
    package.json
  atlas-data/
    catalog/ terms/ structures/ attachments/ functions/ assessments/
    sources/ mappings/ reviews/ manifests/ staging/
  private-sources/                # 필요할 때 생성, 원문·공개 불가 자료
  work/
    STATUS.md DECISIONS.md BLOCKERS.md
    tasks/ reports/ evidence/ review-queue/
```

프로덕션 빌드는 명시적 허용 목록으로 데이터를 가져온다. `private-sources`나 검토용 원문을 public에 복사하지 않는다. 해부학 설명은 출처에 근거해 필요한 범위에서 요약하고 원문 대량 복제는 피한다.

UI 상태는 `selectedMuscleId`, `side`, `selectedPartId`, `activeTab`, `visibleStructures`, `cameraPreset`, `languageMode`로 분리한다. 페이지 URL에는 재현할 수 있는 선택 상태를 넣는다. 컴포넌트에 근육 이름이나 기시·정지 설명을 하드코딩하지 않는다. 검색과 3D 선택은 동일한 ID를 사용한다.

## 8. 성능·접근성의 초기 합격 목표

다음 수치는 성능 실측 결과가 아니라 T02에서 기준 기기를 정한 뒤 검증할 목표다.

- 1440×900, 1024×768, 390×844 화면에서 설명 잘림·가로 넘침·조작 불능 없음.
- 측정 기기·브라우저·네트워크·캐시 조건을 기록. 파일럿 부위 표시 5초 이내, 회전 30fps 이상을 시작 목표로 설정.
- 검색 반응 200ms 이내를 목표로 하며 전신 데이터로 다시 측정.
- 초기 부위 3D 다운로드 15MB 이하를 잠정 예산으로 삼고, 부위별 지연 로딩 적용.
- 30회 부위 전환 뒤 GPU 메모리/컨텍스트 누수가 없는지 확인. 숨기기만 하는 것과 실제 해제의 차이를 검증.
- 키보드로 검색·근육 선택·설명 이동 가능. 색 없이 O/I 구분. 3D 로딩 실패 시 텍스트 접근 가능.

품질을 해치며 예산 숫자만 맞추지 않는다. 어려우면 측정값과 선택지를 DECISIONS에 남기고 LOD·부위 분할을 먼저 적용한다.

## 9. 향후 치료 연결

현재는 치료 탭을 노출하지 않는다. 안정된 근육/기능/검사 ID만 유지하면 나중에 치료 모듈을 별도 연결할 수 있다. 그 단계에서 적응 조건·금기·위험·근거·사람의 결정 경계를 새로 설계한다. 지금 특정 평가 결과에서 침 위치나 치료법으로 연결하는 규칙을 만들어 두지 않는다.

## T10 개정 — 학습 화면과 제작 화면

사용자 요구(2026-09-25)에 따른 우선 규칙이다. 학습 기본 `/`는 상단 검색, 왼쪽 간결한 부위/근육 목록, 중앙 큰 3D, 오른쪽 선택 근육의 이름과 구조·기능·평가 한 탭만 보여준다. 흰 카드/밝은 회색 바탕/절제된 청록, 근육 갈색·뼈 아이보리를 사용한다. 출처·자료 상태는 펼쳐 보기로 둔다. task번호, 내부 ID, JSON import/export, annotation 입력 도구는 학습 화면에서 제거한다.

검토 도구는 불필요한 코드가 아니다. 부착면의 수동 검토에는 별도의 제작 프론트엔드가 필요하다. 현재 `/review`는 개발 환경에서만 제공하며 production learner에서 진입하지 않는다. 파일 검증·변환·상태 산출은 Python/Node 도구, 학습 조회는 data/domain 계층, 화면은 ui, 렌더링은 viewer로 분리한다. 현재는 정적 웹앱이며 인증된 운영 백엔드를 이미 구현했다고 하지 않는다. 공유 서버가 필요한 시점에는 별도 인증/권한 설계를 한다.

참고 이미지와 같은 전체 인체를 약속하지 않는다. 현재 BodyParts3D 종아리 파일럿을 유지하고 전신 자산은 배치 확보한다. Three.js는 최초 설계였으나 T08 실제 구현은 자체 WebGL이다. T12에서 어댑터 전환/유지 근거를 검증한다.
