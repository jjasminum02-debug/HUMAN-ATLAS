# T100 이후 효율적 구현 계획

2026-09-29 · 사용자 요청에 따른 Astra 계획 수정. **계획이며 구현 완료 기록이 아니다.**
현재 순서와 상태 원본은 work/EXECUTION.json. 이 문서는 25 설계의 T100 처리 방식과 검증 주기를 구체화한다. 기존 최대 10개 규칙과 충돌하면 아래 규칙이 우선한다. 역사 B01–B04와 freeze는 수정하지 않는다.

## 1. 현재 진단과 목표

B04 보고서 시점 historical remainder는 152개다. 이는 누락 근육 152개가 아니며 동의어·부분·묶음·변이·진짜 미확보가 섞여 있다. 현재 표시 672개 표면과 세 이름 156개 표면도 고유 근육 수와 다르다. 시작 시 최신 산출물을 다시 집계하고 이 숫자를 고정 기대값으로 사용하지 않는다.

10개마다 별도 builder/validator/전체 build/브라우저/긴 보고서를 만드는 운영은 중단한다. 배치는 실패 복구와 의미 검토의 내부 단위이며 매번 사용자 재입력·커밋·새 구현 코드를 요구하는 단위가 아니다. 규칙적인 대응은 전체 자료에 공통 처리하고, 의미가 모호한 항목만 소규모 검토한다. 근거 없는 자동 명칭·geometry 생성은 금지한다.

성공 지표: 필수 target의 검증된 표현, 실제 누락 수, 세 이름을 가진 선택 가능 개념/좌우 표면 수, 12부위 및 필수 양측 coverage, 표시/검색/카드 회귀, 전송 bytes·frame·memory. 보고서 수나 disposition 기록 수는 제품 완성 지표가 아니다.

## 2. 같은 T100 안의 실행 순서

아래는 새 task ID가 아니라 4개 내부 구현 구간이다. 요청당 T100만 수행하되 10개 처리 후 의무 종료하지 않는다. 실행이 중단되면 동일 구간의 미완 항목만 재개한다. 전체 소요 시간이나 네 번의 대화만으로 완료됨을 보장하지 않는다.

### A. 공통 처리기와 앱용 데이터 분리 — 다음 실행

- 기존 main scene/adapter/overlay와 B01–B04 의미 교정, 승모근 교정을 먼저 회귀 입력으로 재사용한다. 새 로더나 원본 취득은 하지 않는다.
- 공통 정규화 테이블과 builder/validator 하나를 사용한다. 역사 스크립트는 재현용으로 보존하지만 신규 배치별 분기·TypeScript 구조체·테스트 복제를 추가하지 않는다. 현재 결과와 같다는 검증 후 현행 생성 경로를 교체한다.
- 개발 원장에는 객체/hash/관계/명칭 근거/실패 이유를 보존한다. 앱용 projection에는 sourceKey, revision, 표시명/alias, kind, region, side, geometry 연결, 실제 UI/정책 판단에 필요한 필드만 허용한다. 상세 ledger·실패 로그·이전 상태·로컬 파일 경로·출처 원문은 보내지 않는다. 필수 출처 표시는 앱 정보용 별도 요약으로 유지한다.
- 기존 validateIntegration의 권리·hard hold·선택 불가 검사를 삭제해 용량을 줄이지 않는다. 원장 검증은 빌드/서버에서 하고 앱에는 검증된 정책 결과와 필요한 방어 필드를 전달한다. schema/revision/hash를 묶고 stale 데이터는 거부한다. 모든 금지/숨김 상태는 회귀 테스트한다.
- schema를 변경해도 안정적인 sourceKey/URL/선택과 사용자 layer-off를 유지한다. 성능 예산을 높이지 않는다. 앱 JSON raw bytes, 압축 추정 bytes, parse 측정, JS bundle, 모델 chunk를 별개로 비교한다. gzip 추정은 실제 서버 압축이라고 주장하지 않는다.
- 현재 로컬 Vite 제공 경로와 정적 배포는 구별한다. build 통과만으로 dist 단독 실행·공개 배포를 완료라 하지 않는다. 이번에 배포하지 않는다.
- 출력: 공통 현재 원장/생성 경로, 경량 앱 projection, 데이터 동등성·policy 보존·payload 감소 검증. 목표는 상세 evidence가 늘어도 앱 전송 필드가 같이 늘지 않는 구조다.

### B. 전체 명칭과 반복 구조 일괄 연결

- 이미 화면에 보이지만 한국어 이름이 없는 근육/뼈부터 처리한다. 좌우 표면마다 같은 명칭을 새로 조사하지 말고 개념 단위 검증을 재사용한다.
- 기존 용어 자료·동결 TA·검증된 한국어 출처를 먼저 색인한다. 외부 조회는 결측/충돌만 한다. 제공된 엑셀은 검증된 이름의 참고 자료로 사용할 수 있으나 미검증 기시정지·작용 본문을 T100에 넣지 않는다.
- 척추/갈비뼈/손발 등은 근거 있는 segment/side/part 규칙과 예외표로 처리한다. fuzzy matching은 후보 생성만 허용하며 자동 binding 근거가 아니다. 부분을 전체 근육과 동일시하지 않는다.
- 전체 historical remainder와 아직 이름이 없는 표시 구조는 서로 다른 목록으로 관리한다. remainder만 끝내고 이름이 완성됐다고 하지 않는다.
- 자동 schema/hash/중복/잘못된 좌우/필수 값 검사는 전수 실행한다. 새 의미 규칙은 각 유형·좌우·예외의 실제 형상 표본과 대조한다. 의심 항목은 별도 예외 목록으로 보내고 나머지 정상 작업을 계속한다.

### C. 예외와 실제 누락 해결

- 미처리를 synonym, part/group relation, optional variant, actual missing geometry, conflicting identity, unresolved terminology로 구분한다. 그룹/변이를 정리했다고 필수 missing geometry가 해소되는 것은 아니다.
- 공통 snapshot의 object/parent/collection과 실제 평가 geometry를 먼저 확인한다. 다른 파일 취득은 실제 없는 필수 구조에 한정한다. 변환·정합·권리 근거를 확보한 항목만 통합한다. 원본을 수정하거나 반사 복제로 없는 좌우를 만들지 않는다.
- 새 단서 없는 같은 이름 검색은 반복하지 않는다. source 후보·확인한 locator·실패 원인·다음 실제 조치 한 줄을 남기고 독립 작업을 계속한다. 필수 누락이 남으면 T100 partial을 정확히 유지한다.
- 예외 수에 맞춰 5–10개 수준의 의미 검토 묶음을 사용할 수 있지만 전체를 강제로 같은 크기로 자르지 않는다. 부분 성공을 전신 완료로 바꾸지 않는다.

### D. 최종 통합 검사와 인계

- 542 targets/563 memberships/12 regions를 보존하고 전체 target의 현재 disposition 및 필수 표시·선택·명칭 기준을 전수 확인한다. 기존 승인 상태 교정은 유지한다.
- 일반 앱에서 12부위, 복수 선택/전체 복귀, 양측 견갑골·상완·손발, 광배근·얼굴·요추·엉치뼈·골반바닥, 이름 검색, 카드, 주변 흐림/숨김/undo, 카메라 연속성을 검사한다.
- 전체 현재 runtime 검사·typecheck/build·payload/활성 triangles/cache 예산·실제 responsive UI를 최종 실행한다. historical 실패를 덮어쓰지 않는다.
- 모든 필수 기준을 충족한 경우에만 T100 passed. 미달이면 정확한 필수 gap/다음 조치를 기록하며 T80로 떠넘기지 않는다. 완료 후에도 T80/T58 자동 실행 금지.

## 3. 검증·기록·시간·Git 운영

- 데이터만 바뀐 내부 묶음: 공통 schema/semantic/중복/변경 항목 검증. 소스가 안 바뀌면 대형 원본 hash·Blender export·전체 asset 검사를 매번 반복하지 않는다. 검증 재사용은 입력 hash+도구 버전에 묶는다.
- 공통 builder/schema/loader/UI 변경: 영향받는 회귀, typecheck/build, 실제 선택 화면을 즉시 검사한다. 최종 통합 시 전체 검사는 필수다. 중간 실패나 회귀 우려가 있으면 추가 검증한다.
- 일반 데이터 이름 추가마다 새로운 테스트 파일 대신 공통 계약을 전수 검사한다. 특정 실패 재현 테스트는 유지한다.
- 현재 상태 요약 하나와 항목별 원장 하나를 사용한다. batch 증거 원문은 보존하되 매번 전체 자료/스크린샷/기준선을 복제하지 않는다. 변경 hash·행 차이·새 출처만 추가한다.
- 조사/변경/검증 소요 시간과 제품 진척 delta를 기록한다. 30분 동안 새 이름·관계·누락 해결·재사용 가능한 기능이 전혀 늘지 않으면 반복 원인을 점검하고 접근을 바꾼다. 이는 강제 중단·합격·사용자 승인 규칙이 아니다.
- 시작/종료 기준선은 실행당 한 번, 내부 체크포인트는 delta로 충분하다. A 완료, 의미 있는 B/C 통합, 최종 D 통과 시 검증된 소유 변경만 로컬 커밋한다. 10개마다 의무 커밋하지 않는다. 중단 시 작동하는 검증 범위만 정확한 미완 메시지로 체크포인트한다. 원본/사용자 WIP를 혼합하지 않으며 push/배포는 하지 않는다.
- 기본 구현은 Luna Max. 공통 schema/cache 구조 문제를 해결하지 못할 때만 정확한 재현과 차이를 Sol High에 인계할 수 있다. 자동 새 대화 생성/위임은 하지 않는다. 최종 그래픽은 기존 T58의 Astra 담당을 유지한다.
