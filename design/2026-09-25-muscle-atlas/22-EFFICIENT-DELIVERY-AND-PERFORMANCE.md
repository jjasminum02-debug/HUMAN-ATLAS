# 실행 계획 정정 — 반복 데이터 묶음, 제품 완성 기준, 코드·성능 예산

2026-09-28 · 사용자 요청에 따른 계획 개정. 앱 구현을 진행한 문서가 아니다. 충돌하는 19/20/21과 오래된 붙여 넣기 프롬프트보다 이 문서 및 최신 registry를 우선한다. T78 보고서/evidence와 완료한 작업 이력은 보존한다.

## 정정과 완성 범위

T78에서 **잠정 556개 용어 후보를 10개씩 나누자마자 T110–T165라는 56개 사용자 실행 task로 만든 것은 과도한 사전 분할**이었다. 해부학적 분모조차 아직 의미 검증 전이므로 최적 실행 단위가 확정된 상태도 아니었다. 작은 검증 단위는 필요하지만 각 단위마다 새 task·명세·프롬프트·별도 코드가 필요한 것은 아니다.

**T165는 프로젝트 완료 번호가 아니었다.** 이전 T110–T165는 구조 식별/이름/선택 연결만 다뤘다. 기시정지 전체 집필, 기능 전체 집필, 같은 모델의 운동, 신경은 그 뒤의 기존 번호 task에서 수행할 계획이었다. 따라서 “T165까지 하면 지금까지 요청한 모든 기능이 완성된다”는 설명은 사실이 아니다. 이번 개정은 작업량과 실제 미확보 모형을 감추지 않으면서 불필요한 task 발급을 줄인다.

완료는 가장 큰 번호가 아니라 다음 제품 단계의 실제 합격으로 판정한다.

| 제품 단계 | 완료 조건 | 기존 책임 task |
|---|---|---|
| 전신 구조/탐색 | 확정한 전체 근육·맥락 뼈 목록, 광배근 포함 누락 해소, 다중 부위 선택, 양측 뼈, 세 이름 검색/카드/선택, 단일 장면과 미니멀 UI, 실제 그래픽/성능 합격 | T95/96/79/97–121 → T80 → T58 |
| 구조·기능 설명 | 전체 확정 근육의 기시정지와 작용, 조건/갈래 차이, 깔끔한 카드 | T81→T82, T83→T84 |
| 근육 움직임 | 사용자가 보던 같은 모델에서 검증된 수축/주변 신체 움직임, 카메라/레이어 유지, 전체 대상의 대표 작용 범위 검증 | T35, T59/60/25 및 기존 motion queue → T85 |

| 평가·경혈 | 주요 검사 시범, 경혈/경락 등은 이전처럼 별도 후속 설계/허가 범위 | deferred T67 등 / T68 |

모든 해부학적 변이를 항상 실물로 표현한다는 무한 범위를 암묵적으로 약속하지 않는다. T96이 표준 성인 골격근·부분·군·반복 구조·변이의 포함 규칙을 명시하고 필수/변이·선택 범위와 미확보를 분리한다. 자료가 없다고 필수 대상을 삭제해서 합격률을 올리지 않는다. 공개 배포 권리는 로컬 학습용 구현과 별도다.

## 큰 패키지를 안전하게 처리하는 방법

- 외부 task는 한 부위/하나의 계약 변경으로 제한하고, 내부 work-unit은 최대10개 해부학 target 또는 동일 검증 절차의 작은 source 집합이다. 새 rig/clip은 여전히 하나/검증된 작용군 단위다.
- 패키지 manifest에 `taskId`, `revision`, `inputHashes`, 전체 `targetIds`, `workUnits`, 항목별 `states`, `nextUnit`를 둔다. data JSON이 공통 파이프라인을 구동한다. task마다 decoder/viewer/schema를 복제하지 않는다.
- 실행 전 exact 목록을 고정하고 이번 요청에서 그 task를 수행한다. 작업이 끝나지 않았다면 같은 ID로 checkpoint와 다음 unit을 남겨 재개한다. 내부10개가 끝났다는 이유로 다음 task를 실행하거나 새 숫자를 발급하지 않는다. 필수 항목이 남으면 task 완료가 아니다.
- 커밋은 검증된 부위 package 완료 시 또는 장기 작업의 재개 가능한 내부 checkpoint에 남긴다. 메시지에 부분 완료 범위를 정확히 적고 마지막 검증 상태를 기록한다. 파일별 소유권과 기존 WIP 보존 규칙은 동일하다.
- **T81/T83/T87/T89/T91 등 기존 대량 데이터 단계에도 이 원칙 적용:** 10개마다 정수 task를 자동 발급하라는 이전 문구는 폐기한다. 각 단계 안의 고정 지역/계통 manifest와 같은 task 재개를 쓴다. 전체 gate와 내부 검증 상한은 유지한다.
- 새로운 task가 필요한 경우는 새로운 source family/좌표계/변형 방식/공유 계약 등 **기술적 위험이 다른 독립 산출물**일 때다. 먼저 기존 task의 제한된 수정/재개로 해결 가능한지 확인한다. 새 번호 제안에는 기존 작업으로 처리할 수 없는 이유, exact 입력/산출물, 합격 기준과 후반 일정 영향을 함께 남긴다. 사용자에게 숫자 목록만 끝없이 늘려 주지 않는다.
- 이번 개정은 새 task를 한 개도 추가하지 않는다. 미래 버그나 실제 파일 부재가 있을 수 있으므로 “추가 작업이 절대 없다/165가 확정 종료 번호”는 보장하지 않는다. 같은 원인의 재검색/보류 보고서는 새 task로 반복하지 않는다.

## 공통 코딩 기준 — 실제 앱에 필요한 코드만

1. 근육 하나마다 컴포넌트·페이지·renderer·loader를 만들지 않는다. 구조 카드/검색/선택/레이어/모션 명령은 공통 구현, 차이는 데이터와 검증된 asset binding으로 표현한다.
2. scene/root/renderer/camera는 하나. 여러 부위가 공유하는 node는 하나이고 source ID/hash를 보존한다. 지역/레이어 추가로 동일 geometry를 다시 다운로드·복제하지 않는다.
3. source 조사·변환·hash/권리 검사와 대규모 원자료는 오프라인 도구/evidence에 둔다. 브라우저에는 필요한 runtime manifest와 compact 학습 overlay만 전달한다. `work/`, 원본 archive, debug/검증 자료를 production bundle에 넣지 않는다.
4. 이미 있는 ResourceQueue·취소/중복 방지·해제·캐시·search index를 먼저 재사용한다. 새 전신 프레임워크나 전역 상태 라이브러리는 구체적인 재사용 불가 근거가 있을 때만 검토한다. 단순 데이터 증가에 의존성을 추가하지 않는다.
5. data-only package에서는 앱 engine 변경이0인 것이 기본이다. 변경이 필요하면 공통 결함을 한 번 고치고 영향을 검증한다. 런타임에 `if task == Txxx`식 분기를 쌓지 않는다. 역사 변환 스크립트 이름과 사용자용 runtime API는 구분한다.
6. 매 task가 모든 과거 테스트를 무작정 반복하지 않는다. 데이터: schema/참조/hash/중복/정책/해당 부위 실제 표시. 공유 loader/lifecycle 변경: 취소·중복·해제·전환 회귀와 영향 부위. 최종 gate: 전체 UI/성능/coverage.

## 성능 검증과 책임

현재 코드를 읽어 확인한 재사용 가능한 기반은 단일 scene/renderer, 동시 취득 제한2, 필요 부위 chunk 요청, 늦은 응답 취소·해제, DPR 상한1.75, dirty 상태에서만 draw 호출이다. 정적일 때 renderer.draw를 생략해도 animation loop callback/controls update 자체는 현재 계속 돈다. **이미 완벽하게 가볍다는 뜻은 아니다.**

`ResourceQueue.loaded`는 읽은 chunk를 scene 종료까지 보유한다. 무제한 누수라는 증거는 없지만 전신 dataset이 커지면 최대 보유량도 커지는 구조다. T77 manifest는30chunks/68,126,860bytes다. T58 역사 측정의70MB/2.5M triangles/520 draw calls/70MB CPU geometry/p95 33.3ms 검토 상한은 모든 기기 합격이나 최신 T77 실측치가 아니다.

**모든 모형 추가 task의 필수 성능 evidence:**

- 변경 전/후, 같은 브라우저·기기·viewport·DPR·시점에서 transferred/decoded bytes, visible triangles/draw calls, geometry/material 수, CPU geometry bytes, 프레임 p50/p95를 비교한다. 측정 불가 GPU 전체 메모리는 null로 둔다.
- 최초 빈 캐시 로딩과 warm 지역 전환을 구분한다. 초기 all-region은 전신을 점진적으로 완성하되 로딩이 끝났다고 일찍 표시하거나 빠진 구조를 숨겨 성능 합격하지 않는다. cold load 기기/네트워크 조건을 먼저 고정하고 시간을 측정한다.
- 전신↔부위와 레이어 전환을20회 반복해 같은 입력에서 resource 수와 bytes가 계속 늘지 않는지 확인한다. 선택/재시도/context loss에서도 renderer1개, node ID 중복0, 해제 후 잔존 resource와 abort된 늦은 응답을 점검한다.
- T58의 역사 검토 상한을 첫 경보선으로 사용한다. 상한 초과 또는 같은 조건의 p95 20% 이상 악화는 설명 없이 통과시키지 않는다. 전체 비교 조건/새 목표를 기록하고 최적화 또는 미달을 보고한다. 내용이 늘었다는 이유만으로 예산을 자동 상향하지 않는다. 실제 모바일이 없으면 desktop390px 측정을 모바일 합격이라고 쓰지 않는다.
- 최적화는 측정된 병목에 맞춰 필요한 부위/LOD 지연 로딩, geometry/material 재사용, byte-budget cache와 inactive resource 해제 등을 선택한다. 새 LOD는 원본을 건드리지 않고 side/identity/부착 관계·근접 형상 품질을 검증해야 한다. 근육 선택 ID를 잃는 무조건 mesh 합치기나 화면에서 구조를 숨기는 최적화는 금지한다.

자료 취득 task는 자신의 asset delta와 실제 화면·성능을 책임진다. 공통 로더 정책에 구조적 수정이 필요하면 관련 task 안에서 제한된 수정 범위를 기록하거나 T58 품질 gate에 명시적으로 인계한다. 그 경우 전체 품질을 합격 처리하지 않는다. T58(Astra)은 전체 그래픽/성능 gate를 책임지고, 이 문서만으로 최적화 구현을 완료했다고 쓰지 않는다.

## Goal과 진행 제한

이번 대화의 Goal은 **계획 압축·완료 기준·성능 계약·현행 프롬프트 정합성을 검증하고 커밋하는 것**이다. 앱 구현이나 다음 task 수행을 포함하지 않는다. 이 Goal 달성 후 멈춘다.

후속 작업에서 Goal을 사용할 경우에도 “Atlas 전체 완성” 대신 요청된 하나의 부위/기능 task의 실제 산출물과 합격 기준만 목표로 둔다. Goal은 반복 실행과 범위 확장을 정당화하지 않는다. 요청하지 않은 token budget을 임의 설정하지 않는다. 같은 원인으로 막히면 같은 검색/변환을 반복하지 말고 실제 새 증거가 필요한 지점을 분리한다. 자료 부재/권리 미확정 등 입력이 변하지 않는 경우, 재개 체크포인트와 필요한 조건을 남기고 해당 작업에서 멈춘다. 독립 다음 작업은 다음 프롬프트로만 제시한다.

완료 보고는 매번 **이번에 실제 달라진 제품 행동/확보한 geometry → 검증 결과 → 남은 필수 gap → 같은 task 재개인지 다음 ID인지**를 적는다. 계획 문서 수·task 번호·내부 batch 수는 진도 지표로 쓰지 않는다. 실측 성능 악화나 필수 형상 오류를 완료라는 말로 덮지 않는다.
