# Luna 직렬 실행서

## 1. 운용 원칙

한 번에 한 task, 하나의 검증 가능한 결과를 만든다. 코드 작성 → 관련 검증 → 보고 → 다음 task 선택 순서다. 첫 작업은 T00이며, 이 문서의 task를 이미 완료된 것으로 취급하지 않는다. 모델이 구현해야 할 명령과 파일은 미래 산출물이다.

대화 기억에 의존하지 않는다. `work/STATUS.md`, 각 task 명세, 보고서, 실제 파일이 인계 기준이다. 공식 Codex 가이드 역시 범위·맥락·기대 결과와 지속적인 프로젝트 지침을 제공하는 접근을 설명한다. 아래의 구체적인 task 운영 방식은 이 프로젝트에 맞춘 제안이다. [공식 가이드](https://learn.chatgpt.com/guides/best-practices)

### 작업 크기

- 코드 task는 한 기능이나 한 변환 단계. 예상이 커지면 T08a/T08b처럼 구현 전 분할하고 의존성을 기록한다.
- 해부학 데이터 task는 기본 **최대 10개 근육 개념**. 근두·복잡한 건·출처 충돌이 많으면 3–5개로 줄인다.
- 한 task에서 스키마 변경과 전신 자료 입력을 동시에 하지 않는다.
- 버그 수정은 실패 테스트/재현 사례를 먼저 기록하고 해당 문제만 고친다.
- 한 모델이 작성·검토해도 독립 전문가 검토가 되지는 않는다. AI review라고 정확히 적는다.

### task 상태

`todo → doing → technical_pass → complete`

다른 상태: `blocked_external`, `needs_human_review`, `failed`.

`complete`는 해당 task 산출물과 검증 기준 충족을 뜻한다. 데이터 추출 task는 미확인 항목을 정확히 분리하고 목록을 만들면 기술적으로 complete일 수 있다. 하지만 그 항목의 해부학 리뷰나 전신 릴리스 gate가 자동 완료되는 것은 아니다. 리뷰 task는 사람 확인 없이 complete로 올리지 않는다.

## 2. 반복 프롬프트

같은 작업에서 이어가든 새 작업을 열든 아래 문장을 사용한다.

```text
design/2026-09-25-muscle-atlas/00-START-HERE.md,
03-LUNA-SERIAL-RUNBOOK.md, work/STATUS.md를 읽어라.
STATUS의 NEXT_TASK가 실제 선행 조건을 만족하는지 확인하고 그 task 하나만 수행해라.
명세에 필요한 상세 설계와 직전 보고서를 읽고, 실제 파일 상태를 확인한 뒤 시작해라.
완료 기준을 낮추거나 테스트를 생략해 통과시키지 마라.
원본 OpenSim_Models와 기존 사용자 변경을 보존해라.
출처 없는 해부학·한자·좌표·평가 설명을 추측으로 채우지 마라.
작업 범위 내 문제는 해결하고, 자료 부족은 BLOCKERS 및 review-queue에 기록해라.
검증 명령/결과/실행하지 못한 항목을 보고서로 저장하고 STATUS를 갱신해라.
마지막에 완료한 ID, 검증 결과, 미확인 사항, 다음 ID와 다음 프롬프트를 알려주고 멈춰라.
```

특정 task를 실행하려면 첫 부분을 “T09만 수행해라”로 바꾼다. “전체를 알아서 완성”이라는 요청으로 매번 범위를 넓히지 않는다. 새 task에서도 위 파일만 읽으면 이어갈 수 있다.

## 3. 매 task의 공통 입출력

시작할 때 `work/tasks/Txx.md`를 만든다. 반드시 목적, 선행 task, 읽을 파일, 쓸 수 있는 경로, 산출물, 합격 기준, 범위 밖 항목을 적는다. 기준은 작업 후에 낮추지 않는다.

종료 시 `work/reports/Txx.md`에 변경 파일, 검증 명령과 exit code, 결과, 증거 경로, 미실행 검사, 의학적 미확인 사항, 다음 작업을 적는다. 화면을 바꿨다면 브라우저에서 해당 행동을 실제 수행하고 `work/evidence/Txx/`에 화면/콘솔 결과를 남긴다. build만으로 UI 검증 완료라 하지 않는다.

Git 사용 가능하면 작업 전 diff를 확인하고 기존 변경과 섞지 않는다. 별도 저장소가 없다면 T00에서 구조를 정리하되 큰 원본 데이터 전체를 무조건 추적하지 않는다. 각 task 완료 후 사용자 변경이 포함되지 않은 체크포인트를 남긴다. 자동 push나 배포는 하지 않는다.

## 4. 준비 및 파일럿 — T00~T14

### T00 — 실행 기반 만들기

- 선행: 없음. 입력: 이 설계 패키지, 기존 프로젝트 파일.
- 작업: 기존 AGENTS/Git/앱 유무 확인. `work/STATUS.md`, DECISIONS, BLOCKERS, task/report 폴더 생성. templates를 작업용 복사본으로 사용. 해당 프로젝트에 필요한 지침만 AGENTS에 추가하며 기존 지침은 보존.
- 산출물: 실제 작업 경로, 원본 읽기 전용 규칙, task 상태표, NEXT_TASK=T01.
- 통과: 설계·샘플과 실제 학습 데이터를 구분하고 원본 변경 없음. 앱 구현은 아직 하지 않음.

### T01 — 전신 범위와 출처 정책 고정

- 선행: T00. 입력: 01의 전신 범위, 04의 출처 후보.
- 작업: 명칭 기준 판본 후보, 해부학 근거, 평가 근거, 3D 라이선스/귀속 양식 작성. 파일·판본·locator를 확보한 것과 확보 못 한 것을 구분. 대상 부위와 근군/근두/좌우 집계 규칙을 고정.
- 산출물: `atlas-data/manifests/scope.json`, `atlas-data/sources/registry.json`, `work/review-queue/source-gaps.md`.
- 통과: 모든 부위가 포함되거나 명시적 제외 이유가 있음. 실제 전체 항목 목록은 T04에서 작성. 무단 원문 복사나 유료 자료 구매는 하지 않음.

### T02 — 3D 자산 타당성 파일럿

- 선행: T01. 작업: BodyParts3D 후보에서 오른쪽 종아리 6개 근육과 관련 뼈/부착 구조의 가용성·이용 조건·원본 ID 조사. 허용된 자산은 소량만 가져와 형태를 점검. 기존 OpenSim 파일은 비교용으로만 확인.
- 산출물: asset manifest, 파일 hash, 좌표/단위/포즈 결정, 종아리 한 부위의 뷰어 시험 결과, 기준 기기, 누락 표.
- 통과: 적어도 한 실제 근육·관련 뼈가 올바른 좌우/방향으로 함께 보이고 source ID를 추적 가능. 6개 전체의 지원 여부가 명확함.
- 실패 분기: 자산 접근/조건/형태 문제면 `blocked_external` 에셋 task를 만들고 개념도/텍스트 기반 UI 개발을 계속. **이 경우 3D 파일럿 gate는 통과 아님.** 대체 메시를 모델이 임의로 생성해 정확한 근육으로 선언하지 않음.

### T03 — 공통 스키마와 검증기

- 선행: T01, T02에서 좌표 계약 확정(실제 자산 미확보여도 계약은 확정 가능).
- 작업: 02의 핵심 엔터티 스키마, 교차 참조/리뷰/공개 규칙 검증 구현. 기능·평가는 최소 확장 계약만 정의하고 데이터 입력은 뒤로 미룸.
- 산출물: `atlas-data/schemas/`, validator, 양성/음성 fixtures, 검증 명령.
- 통과: 고아 ID, 좌우 오류, 오래된 annotation, 근거 없는 reviewed가 실패. 스키마 파일이 존재하는지만 검사하는 방식 금지.

### T04 — 전체 근육 목록과 언어 정책

- 선행: T03. 작업: 접근 가능한 표준 판본에서 전신 개념 목록을 구성하고 근군/개별/근두/변이를 구분. 판본의 장/항목과 대응.
- 산출물: canonical catalog, region tree, source crosswalk, 목록 누락/미해결 기록, vocabulary policy.
- 통과: 각 항목에 안정 ID, 분류, 출처 위치 또는 미확인 상태. 전신 분모가 검토 가능한 형태로 동결됨. 출처 미확보면 부분 목록으로 명시하고 전신 gate 차단; T05~파일럿은 진행 가능.

### T05 — 파일럿 6개 근육의 명칭·구조 텍스트

## 8. 필수 검증 명령 — T03/T06에서 구현할 인터페이스

아래 npm 인터페이스는 최초 설계의 목표다. 현재 실제 명령은 atlas-web에서 `pnpm typecheck`, `pnpm test:search`, `pnpm test:annotations`, `pnpm validate:learning`, `pnpm build`; 루트에서 `python3 atlas-data/schemas/validate.py --check-schemas`, `--fixtures`, `--dataset atlas-data/catalog/canonical-catalog.json`이다. 아직 없는 validate:data/test:e2e/report:coverage를 실행했다고 보고하지 않는다.

```text
npm run validate:data     # 실제 스키마, 참조, provenance, stale, publication
npm run typecheck
npm run test              # 의미 있는 도메인/실패 사례
npm run build
npm run test:e2e          # 실제 사용자 흐름
npm run report:coverage   # 동결 catalog 분모 기준
```

코드 변경에는 관련 단위 검사와 타입/빌드, 화면 변경에는 해당 브라우저 시나리오, 데이터 변경에는 스키마·참조·출처·coverage 검사를 적용한다. task마다 무조건 전체 전신 테스트를 반복할 필요는 없다. gate에서는 전체 관련 검사를 수행한다. 검증 도구 미설치·브라우저 불가·네트워크 실패는 “통과”가 아니라 “미실행”이다.

## 9. 실패와 선택의 규칙

| 상황 | Luna가 할 일 | 사용자에게 필요한 일 |
|---|---|---|
| 단순 코드/타입/연결 오류 | 재현→수정→관련 검사, 범위 유지 | 없음 |
| 같은 원인으로 수정 2회 후에도 실패 | 더 넓게 손대지 말고 최소 재현·로그·가능 원인 작성 | 해당 차단 작업만 검토 필요할 수 있음 |
| 원문·한자 출처 없음 | 결측/미확인, 다른 항목 진행 | 사용할 교재/용어집 지정 또는 자료 제공 |
| 두 출처가 충돌 | 판본/문맥 차이 기록, 하나로 합성하지 않음 | 필요하면 채택 기준 판단 |
| 메시 없음/합쳐짐 | text_only/partial geometry 표기 | 완전 3D를 위해 별도 자산 확보 가능 |
| 실제 부착면 판단 필요 | 후보와 다각도 검토 패킷 | 위치·범위 검토 |
| 코드 gate 통과, 의학 리뷰 대기 | 독립 task 계속, 해당 학습 출판 보류 | review queue에서 묶음 확인 |
| 스키마 수정 필요 | 이유·영향·migration·검사를 작은 task로 추가 | 의미/범위 바뀌는 경우만 결정 |
| 유료 자산/새 공개/배포 | 결과·비용/조건을 구체화하고 실제 실행 전 확인 | 구매/공개 의사 결정 |

모든 task마다 사용자를 부르지 않는다. 사용자가 확인할 내용은 `work/review-queue/`에 묶고, “어떤 문장/어떤 위치가 왜 미확인인지”를 구체적으로 제시한다. 독립적인 기술 작업은 계속할 수 있다. 단, 묵묵히 동의한 것으로 간주해 사람 리뷰를 자동 승인하지 않는다.

## 10. 어느 시점에 새 작업을 열 것인가

동일한 기능의 짧은 연속 작업은 같은 대화에서 계속해도 된다. 준비→뷰어→전신 배치→기능→평가처럼 성격이 바뀌거나 대화가 길어지면 새 작업을 열고 반복 프롬프트를 사용한다. 한 작업이 이전 작업의 완료 보고만 믿지 않고 파일/검증 결과를 읽도록 한다.

프로젝트 완료는 task 개수로 판단하지 않는다. 동결한 전체 목록, 출처가 있는 내용, 검토된 부착부, 실제 브라우저 경험, 누락의 공개가 함께 충족되어야 한다.
