# Luna 직렬 실행서

## 1. 운용 원칙

한 번에 한 task, 하나의 검증 가능한 결과를 만든다. 코드 작성 → 관련 검증 → 보고 → 다음 task 선택 순서다. 첫 작업은 T00이며, 이 문서의 task를 이미 완료된 것으로 취급하지 않는다. 모델이 구현해야 할 명령과 파일은 미래 산출물이다.

대화 기억에 의존하지 않는다. `work/STATUS.md`, 각 task 명세, 보고서, 실제 파일이 인계 기준이다. 공식 Codex 가이드 역시 범위·맥락·기대 결과와 지속적인 프로젝트 지침을 제공하는 접근을 설명한다. 아래의 구체적인 task 운영 방식은 이 프로젝트에 맞춘 제안이다. [공식 가이드](https://learn.chatgpt.com/guides/best-practices)

### 작업 크기

- 코드 task는 한 기능이나 한 변환 단계. 예상이 커지면 T08a/T08b처럼 구현 전 분할하고 의존성을 기록한다.
- 해부학 데이터 task는 기본 **최대 10개 근육 개념**. 근두·복잡한 건·출처 충돌이 많으면 3–5개로 줄인다.
- 한 task에서 스키마 변경과 전신 자료 입력을 동시에 하지 않는다.
- 버그 수정은 실패 테스트/재현 사례를 먼저 기록하고 해당 문제만 고친다.
- 한 모델이 작성·검토해도 독립 전문가 검토가 되지는 않는다. AI review라고 정확히 적는다.

### task 상태

`todo → doing → technical_pass → complete`

다른 상태: `blocked_external`, `needs_human_review`, `failed`.

`complete`는 해당 task 산출물과 검증 기준 충족을 뜻한다. 데이터 추출 task는 미확인 항목을 정확히 분리하고 목록을 만들면 기술적으로 complete일 수 있다. 하지만 그 항목의 해부학 리뷰나 전신 릴리스 gate가 자동 완료되는 것은 아니다. 리뷰 task는 사람 확인 없이 complete로 올리지 않는다.

## 2. 반복 프롬프트

같은 작업에서 이어가든 새 작업을 열든 아래 문장을 사용한다.

```text
design/2026-09-25-muscle-atlas/00-START-HERE.md,
03-LUNA-SERIAL-RUNBOOK.md, work/STATUS.md를 읽어라.
STATUS의 NEXT_TASK가 실제 선행 조건을 만족하는지 확인하고 그 task 하나만 수행해라.
명세에 필요한 상세 설계와 직전 보고서를 읽고, 실제 파일 상태를 확인한 뒤 시작해라.
완료 기준을 낮추거나 테스트를 생략해 통과시키지 마라.
원본 OpenSim_Models와 기존 사용자 변경을 보존해라.
출처 없는 해부학·한자·좌표·평가 설명을 추측으로 채우지 마라.
작업 범위 내 문제는 해결하고, 자료 부족은 BLOCKERS 및 review-queue에 기록해라.
검증 명령/결과/실행하지 못한 항목을 보고서로 저장하고 STATUS를 갱신해라.
마지막에 완료한 ID, 검증 결과, 미확인 사항, 다음 ID와 다음 프롬프트를 알려주고 멈춰라.
```

특정 task를 실행하려면 첫 부분을 “T09만 수행해라”로 바꾼다. “전체를 알아서 완성”이라는 요청으로 매번 범위를 넓히지 않는다. 새 task에서도 위 파일만 읽으면 이어갈 수 있다.

## 3. 매 task의 공통 입출력

시작할 때 `work/tasks/Txx.md`를 만든다. 반드시 목적, 선행 task, 읽을 파일, 쓸 수 있는 경로, 산출물, 합격 기준, 범위 밖 항목을 적는다. 기준은 작업 후에 낮추지 않는다.

종료 시 `work/reports/Txx.md`에 변경 파일, 검증 명령과 exit code, 결과, 증거 경로, 미실행 검사, 의학적 미확인 사항, 다음 작업을 적는다. 화면을 바꿨다면 브라우저에서 해당 행동을 실제 수행하고 `work/evidence/Txx/`에 화면/콘솔 결과를 남긴다. build만으로 UI 검증 완료라 하지 않는다.

Git 사용 가능하면 작업 전 diff를 확인하고 기존 변경과 섞지 않는다. 별도 저장소가 없다면 T00에서 구조를 정리하되 큰 원본 데이터 전체를 무조건 추적하지 않는다. 각 task 완료 후 사용자 변경이 포함되지 않은 체크포인트를 남긴다. 자동 push나 배포는 하지 않는다.

## 4. 준비 및 파일럿 — T00~T14

### T00 — 실행 기반 만들기

- 선행: 없음. 입력: 이 설계 패키지, 기존 프로젝트 파일.
- 작업: 기존 AGENTS/Git/앱 유무 확인. `work/STATUS.md`, DECISIONS, BLOCKERS, task/report 폴더 생성. templates를 작업용 복사본으로 사용. 해당 프로젝트에 필요한 지침만 AGENTS에 추가하며 기존 지침은 보존.
- 산출물: 실제 작업 경로, 원본 읽기 전용 규칙, task 상태표, NEXT_TASK=T01.
- 통과: 설계·샘플과 실제 학습 데이터를 구분하고 원본 변경 없음. 앱 구현은 아직 하지 않음.

### T01 — 전신 범위와 출처 정책 고정

- 선행: T00. 입력: 01의 전신 범위, 04의 출처 후보.
- 작업: 명칭 기준 판본 후보, 해부학 근거, 평가 근거, 3D 라이선스/귀속 양식 작성. 파일·판본·locator를 확보한 것과 확보 못 한 것을 구분. 대상 부위와 근군/근두/좌우 집계 규칙을 고정.
- 산출물: `atlas-data/manifests/scope.json`, `atlas-data/sources/registry.json`, `work/review-queue/source-gaps.md`.
- 통과: 모든 부위가 포함되거나 명시적 제외 이유가 있음. 실제 전체 항목 목록은 T04에서 작성. 무단 원문 복사나 유료 자료 구매는 하지 않음.

### T02 — 3D 자산 타당성 파일럿

- 선행: T01. 작업: BodyParts3D 후보에서 오른쪽 종아리 6개 근육과 관련 뼈/부착 구조의 가용성·이용 조건·원본 ID 조사. 허용된 자산은 소량만 가져와 형태를 점검. 기존 OpenSim 파일은 비교용으로만 확인.
- 산출물: asset manifest, 파일 hash, 좌표/단위/포즈 결정, 종아리 한 부위의 뷰어 시험 결과, 기준 기기, 누락 표.
- 통과: 적어도 한 실제 근육·관련 뼈가 올바른 좌우/방향으로 함께 보이고 source ID를 추적 가능. 6개 전체의 지원 여부가 명확함.
- 실패 분기: 자산 접근/조건/형태 문제면 `blocked_external` 에셋 task를 만들고 개념도/텍스트 기반 UI 개발을 계속. **이 경우 3D 파일럿 gate는 통과 아님.** 대체 메시를 모델이 임의로 생성해 정확한 근육으로 선언하지 않음.

### T03 — 공통 스키마와 검증기

- 선행: T01, T02에서 좌표 계약 확정(실제 자산 미확보여도 계약은 확정 가능).
- 작업: 02의 핵심 엔터티 스키마, 교차 참조/리뷰/공개 규칙 검증 구현. 기능·평가는 최소 확장 계약만 정의하고 데이터 입력은 뒤로 미룸.
- 산출물: `atlas-data/schemas/`, validator, 양성/음성 fixtures, 검증 명령.
- 통과: 고아 ID, 좌우 오류, 오래된 annotation, 근거 없는 reviewed가 실패. 스키마 파일이 존재하는지만 검사하는 방식 금지.

### T04 — 전체 근육 목록과 언어 정책

- 선행: T03. 작업: 접근 가능한 표준 판본에서 전신 개념 목록을 구성하고 근군/개별/근두/변이를 구분. 판본의 장/항목과 대응.
- 산출물: canonical catalog, region tree, source crosswalk, 목록 누락/미해결 기록, vocabulary policy.
- 통과: 각 항목에 안정 ID, 분류, 출처 위치 또는 미확인 상태. 전신 분모가 검토 가능한 형태로 동결됨. 출처 미확보면 부분 목록으로 명시하고 전신 gate 차단; T05~파일럿은 진행 가능.

### T05 — 파일럿 6개 근육의 명칭·구조 텍스트

- 선행: T03, 파일럿 개념 ID 확정.
- 작업: gastrocnemius(근두 구분), soleus, tibialis anterior/posterior, fibularis longus/brevis의 한글 표준/관용명·한자·영어, 기시·정지와 관련 구조를 출처별 입력. 기능·평가 본문은 입력하지 않음.
- 산출물: 6개 개념의 terms, attachments, claims, evidence, missing/conflict queue.
- 통과: 입력값 출처를 역추적할 수 있고 모든 결측이 명시됨. 세 언어 완성과 기시·정지 확정은 실제 검토 결과만 집계.

### T06 — 웹 앱과 텍스트 탐색

- 선행: T03, T05. 작업: React/TypeScript/Vite, 데이터 로더, 오류/미완료 상태, 근육 목록과 구조 카드, URL 선택 상태.
- 산출물: `atlas-web/`, 설치·실행·빌드 명령, lockfile.
- 통과: 6개 데이터가 코드 하드코딩 없이 표시. 3D 자산 없어도 앱과 구조 카드 사용 가능. 모바일/키보드 기본 탐색 확인.

### T07 — 부위별 3D 변환 파이프라인

- 선행: T02의 사용 가능한 실제 에셋, T03. 작업: 원본→GLB 변환, stable mapping, 좌표계/단위/원본 hash 보존. 필요 시 LOD 생성. 반복 변환 시 새 ID를 무작위 발급하지 않음.
- 산출물: 변환 스크립트, region GLB, manifest, attribution.
- 통과: 원본 불변, 실제 메시 ID↔개념 관계 추적, 크기/방향/좌우 확인, 두 번 변환한 의미적 결과 일치. 전신 다운로드는 하지 않음.

### T08 — 3D 선택·격리·카메라

- 선행: T06, T07. 작업: mesh 클릭↔카드 동기화, 목록 선택↔확대, 전체/주변 보기, 숨김/투명화/복원, 정면/후면/측면.
- 산출물: viewer와 UI 연결.
- 통과: 깊은 근육 선택 가능, 숨긴 메시 클릭 차단, 빠른 선택 전환 시 카드/모델 불일치 없음. 실제 브라우저 증거.

### T09 — 부착부 annotation 검토 도구

- 선행: T08. 작업: point/polyline/surface patch 입력·편집·삭제·JSON export/import, 부착 문장 연결, 상태 표시. UI에서 원본 메시를 수정하지 않고 overlay 데이터로 저장.
- 산출물: 검토 모드, annotation 스키마/내보내기.
- 통과: 회전/확대 후 같은 위치에 남음, 재로딩 동일, 좌우/asset revision mismatch 거부. 기준 topology 변경 시 stale. 처음에는 synthetic fixture로 도구 검증.

### T10 — 실제 파일럿 기시·정지 매핑

- 선행: T05, T09. 작업: 각 근육/근두의 근거 문장에 실제 annotation 후보 연결. 넓은 부착부를 대표점만으로 완료 처리하지 않음. 사람 검토용 정면/후면/측면 장면과 목록 생성.
- 산출물: 실제 후보 overlays + review packet.
- 통과: 모델의 추정은 needs_review로 남기고 출처/범위/좌우/근두 확인 가능. 사람이 확정하지 않았으면 anatomy gate는 미통과. 기술 작업은 계속 가능.

### T11 — 다국어 검색·표시

- 선행: T06, T05. 작업: 한글 표준/관용명, 한자, 영어 별칭 검색과 주 언어 설정. 서로 다른 이름이 같은 stable ID로 연결되는지 검증.
- 산출물: 검색 인덱스, 검색 테스트셋.
- 통과: 검증된 각 언어명으로 같은 근육 선택, 없는 용어는 없는 것으로 표시, 유사명 충돌 시 부위·근두 구분. 단순 번역 생성 금지.

### T12 — 출처·리뷰·누락 현황

- 선행: T10, T11. 작업: 주장별 출처 펼침, AI/사람 리뷰 구분, 수정 후 stale, 분모별 coverage 화면, 기본 학습/검토 중 보기 필터.
- 산출물: review queue, coverage report, public manifest 생성 로직.
- 통과: 검토되지 않은 한자/부착 영역이 학습 정답으로 출판되지 않음. 미지원 근육이 검색에서 사라지지 않음.

### T13 — 구조 파일럿 통합 검증

- 선행: T07~T12. 작업: 검색→선택→격리→기시·정지 클릭→출처→복원→재접속 시나리오. 세 화면 크기, 콘솔·실패 로딩·접근성·성능 확인.
- 산출물: 실행 로그, 브라우저 증거, 실패 이슈와 수정 기록.
- 통과: 기술 gate 통과. anatomy gate 미완이면 “기술 파일럿 통과, 내용 검토 대기”로 보고. 테스트를 삭제해 통과시키지 않음.

### T14 — 파일럿 해부학 검토 반영과 전신 확장 준비

- 선행: T13. 작업: 사용자가 제공한 실제 검토 결과를 해당 revision에 기록하고 수정·재검증. 없으면 검토 패킷을 마무리하고 needs_human_review로 남김. 오른쪽 파일럿 검토 전 전신 좌표 대량 생성을 하지 않음.
- 산출물: pilot gate, 수정된 데이터, 확장 가능한 schema/도구 판단.
- 통과: 6개 실제 근육의 용어·기시/정지·형태·좌표를 검토했을 때만 완전 통과. 검토 대기 중 T15의 텍스트/목록 정리는 독립 진행 가능.

## 5. 전신 구조 확장 — 반복 가능한 task 묶음

### T15 — 전신 배치 manifest

- 선행: T04의 검토 가능한 전체 목록, T13의 기술 통과.
- 작업: 각 근육 개념을 정확히 한 구조 입력 배치에 배정. 기본 10개 이하. 좌우/근두는 해당 개념 안에서 관리. 부위 경계를 넘는 근육은 대표 배치 하나에서 작성하고 다른 부위에는 참조.
- 산출물: `work/tasks/batches.json`, 각 Bxx의 muscle ID 목록, 선행 관계, 총 대상 수.
- 통과: 대상 누락/중복 0, 분류별 수 일치, 미확보 자료가 표시됨.

권장 순서: 종아리 나머지→발→넓적다리/엉덩이→어깨/위팔→아래팔/손→등/목→흉곽/복벽→골반저/회음→머리/얼굴/저작→눈/혀/인두/후두. 이 순서는 작업 우선순위이며 마지막 부위를 제품 범위에서 제외하는 의미가 아니다. 실제 목록 분량에 따라 배치 수가 정해지므로 지금 임의의 전신 근육 수를 선언하지 않는다.

각 Bxx는 아래 네 task를 **직렬로** 실행한다.

| Task ID | 작업·산출물 | 합격 기준 |
|---|---|---|
| S-Bxx-A | 명칭·기시/정지 출처 정리, 최대 10개, missing/conflict 포함 | 주장별 근거/결측, 스키마·참조 통과 |
| S-Bxx-B | 해당 부위 에셋/매핑/annotation 후보, 좌우·근두 검증 패킷 | 자산 버전/정합 명시, 지원 불가를 별도 기록 |
| S-Bxx-C | 사람 검토 결과 반영 및 공개 상태 결정 | 실제 검토 없으면 needs_human_review, AI 대신 승인 금지 |
| S-Bxx-D | 검색·표시·출처·회귀 검사, coverage 갱신 | 이전 배치 깨짐 없음, 누락 분모 유지 |

S-Bxx-C에서 사람 리뷰를 기다리면 다음 배치 A처럼 독립 작업을 진행할 수 있다. 이때 해당 배치의 공개 완료를 선언하지 않는다. 좌표 작업은 T14의 파일럿 리뷰 후 확장하며, 텍스트 수집만으로 3D 완료 상태를 올리지 않는다.

### T16 — 전신 구조 릴리스 점검

- 선행: 모든 구조 배치의 산출물과 누락 목록.
- 작업: catalog 대비 명칭/텍스트/메시/좌표를 각각 대조. 누락은 숨기지 않고 지원 표로 제공. 사용자가 읽을 전신 구조 현황과 재현 가능한 release manifest 생성.
- 통과: 모든 대상이 포함되고 릴리스하는 각 claim/좌표가 기준 충족. 미지원이 있으면 `전신 목록 + 부분 구조 자료`로 명명하고 전신 3D 완성이라고 하지 않음.
- 전신 누락을 기다리는 동안 검토 완료된 구조에 대한 기능 작업은 가능. 기본 순서는 구조 우선이며 범위/명칭을 정확히 보고.

## 6. 기능 — T17~T20

### T17 — 기능 엔진과 UI

- 선행: T13, 안정된 구조 계약. 작업: JointAction의 자세/관절/수축 역할/과제 관계, 구조↔기능 탐색, 조건 표시, 미입력 상태 구현.
- 통과: 조건이 다른 기능을 한 문장으로 뭉개지 않음. synthetic fixtures는 실데이터와 분리. 실제 기능 설명 입력은 T18.

### T18 — 파일럿 6개 기능 데이터

- 선행: T17, 해당 구조 검토. 작업: 출처 있는 작용·안정화·과제·조건 설명 작성, 구조 claim과 연결. 정량 생체역학 수치 생성 금지.
- 산출물: 기능 데이터와 검토 패킷.
- 통과: 근거/해석 구분, 관절·자세 조건 검토, 사람 리뷰 대기 항목은 별도.

### T19 — 기능 시각화와 검증

- 선행: T18. 작업: 기준 포즈에 작용 방향 표시 또는 검토된 몇 개 포즈 제공. 모션이 근육 변형/힘 계산을 의미하는지 구분. V1에는 실시간 OpenSim 구동이 필요 없음.
- 통과: 표시 방향·좌우가 내용과 일치, 미검증 좌표가 포즈 변화로 정확해진 것처럼 보이지 않음. 복잡하면 애니메이션 없이 검토된 도식으로 완료.

### F-Bxx — 기능 배치 반복

- 선행: T18/19 파일럿, 각 Bxx 구조 검토. 작업: 같은 최대 10개 목록에 기능 입력→출처/조건 검증→사람 리뷰→통합 검사. 크면 F-Bxx-A/B로 분리.
- 통과: structure와 기능의 개념 ID가 일치하고 전체 누락 목록 유지.

### T20 — 기능 단계 종료

- 선행: 기능 배치 결과. 작업: 조건 검색/관절별 보기/coverage 점검, 기능 릴리스 manifest.
- 통과: 검토 완료 범위만 완성 표기. 모든 근육에 억지로 동일한 종류의 역할을 채우지 않음.

## 7. 평가 — T21~T24

### T21 — 검사 라이브러리와 관계

- 선행: T17의 기능 계약, T20 또는 평가 대상의 기능 검토 완료.
- 작업: 검사 목적/절차/관찰/해석/한계/다음 확인, many-to-many 관계, scope와 protocol variant 구현. 증상 입력 진단기는 만들지 않음.
- 통과: 한 검사→여러 구조, 한 근육→여러 검사, 독립 평가 어려움 모두 표현 가능. 정상 기준·정확도 수치의 출처 규칙 검사.

### T22 — 파일럿 평가 콘텐츠

- 선행: T21. 작업: 파일럿과 관련된 검사 소수부터 출처를 확보해 작성. 근력/저항, 길이/가동성, 지구력/과제 수행 등 확인 목적을 분리. 검사 자세·저항·보상·중단 조건을 상세히 입력.
- 통과: 관찰 사실과 해석이 분리되고 검사 실패→특정 병변 확정 규칙 없음. 전문가 검토 패킷 제공. 출처 없는 검사는 후보 상태.

### E-Bxx — 평가 배치 반복

- 선행: T22의 검토된 예시, 각 대상의 기능 검토.
- 작업: 이미 존재하는 검사 ID를 재사용해 근육별 연결. 별도 검사가 없는 근육은 근군/과제 평가 한계 설명.
- 통과: 검사 중복/상충 프로토콜 발견, 근거·주의/중단·해석 한계 검토. 내용 작업이 크면 검사 3–5개 단위로 분할.

### T23 — 구조→기능→평가 통합 학습

- 선행: T22. 작업: 근육에서 검사까지 이동, 움직임에서 관련 근육 비교, 이름·부착부 퀴즈. 퀴즈는 reviewed 정답만 사용하고 틀린 이유와 출처 제공.
- 통과: 언어 전환·뒤로 이동·deep link에서 선택 상태 일치. 정답 데이터 변경 시 기존 문제 stale. 자동 진단/치료 연결 없음.

### T24 — 최종 로컬 전달

- 선행: 공개할 구조/기능/평가 범위 확정. 작업: 사용자 경로 E2E, 성능, 라이선스/귀속, public/private 분리, 설치/복구/추가 배치 설명.
- 산출물: 최종 앱, release manifest, coverage 표, known issues, 실행 방법, 검토 대기 큐.
- 통과: 기술 검증과 콘텐츠 검토 범위를 각각 보고. 전신 미완 항목이 있으면 목록 포함. 온라인 공개는 이 task에서 자동 실행하지 않음.

## 8. 필수 검증 명령 — T03/T06에서 구현할 인터페이스

다음 명령은 설계상 요구하는 인터페이스이며 현재 실행 가능한 명령이라고 주장하지 않는다.

```text
npm run validate:data     # 실제 스키마, 참조, provenance, stale, publication
npm run typecheck
npm run test              # 의미 있는 도메인/실패 사례
npm run build
npm run test:e2e          # 실제 사용자 흐름
npm run report:coverage   # 동결 catalog 분모 기준
```

코드 변경에는 관련 단위 검사와 타입/빌드, 화면 변경에는 해당 브라우저 시나리오, 데이터 변경에는 스키마·참조·출처·coverage 검사를 적용한다. task마다 무조건 전체 전신 테스트를 반복할 필요는 없다. gate에서는 전체 관련 검사를 수행한다. 검증 도구 미설치·브라우저 불가·네트워크 실패는 “통과”가 아니라 “미실행”이다.

## 9. 실패와 선택의 규칙

| 상황 | Luna가 할 일 | 사용자에게 필요한 일 |
|---|---|---|
| 단순 코드/타입/연결 오류 | 재현→수정→관련 검사, 범위 유지 | 없음 |
| 같은 원인으로 수정 2회 후에도 실패 | 더 넓게 손대지 말고 최소 재현·로그·가능 원인 작성 | 해당 차단 작업만 검토 필요할 수 있음 |
| 원문·한자 출처 없음 | 결측/미확인, 다른 항목 진행 | 사용할 교재/용어집 지정 또는 자료 제공 |
| 두 출처가 충돌 | 판본/문맥 차이 기록, 하나로 합성하지 않음 | 필요하면 채택 기준 판단 |
| 메시 없음/합쳐짐 | text_only/partial geometry 표기 | 완전 3D를 위해 별도 자산 확보 가능 |
| 실제 부착면 판단 필요 | 후보와 다각도 검토 패킷 | 위치·범위 검토 |
| 코드 gate 통과, 의학 리뷰 대기 | 독립 task 계속, 해당 학습 출판 보류 | review queue에서 묶음 확인 |
| 스키마 수정 필요 | 이유·영향·migration·검사를 작은 task로 추가 | 의미/범위 바뀌는 경우만 결정 |
| 유료 자산/새 공개/배포 | 결과·비용/조건을 구체화하고 실제 실행 전 확인 | 구매/공개 의사 결정 |

모든 task마다 사용자를 부르지 않는다. 사용자가 확인할 내용은 `work/review-queue/`에 묶고, “어떤 문장/어떤 위치가 왜 미확인인지”를 구체적으로 제시한다. 독립적인 기술 작업은 계속할 수 있다. 단, 묵묵히 동의한 것으로 간주해 사람 리뷰를 자동 승인하지 않는다.

## 10. 어느 시점에 새 작업을 열 것인가

동일한 기능의 짧은 연속 작업은 같은 대화에서 계속해도 된다. 준비→뷰어→전신 배치→기능→평가처럼 성격이 바뀌거나 대화가 길어지면 새 작업을 열고 반복 프롬프트를 사용한다. 한 작업이 이전 작업의 완료 보고만 믿지 않고 파일/검증 결과를 읽도록 한다.

프로젝트 완료는 task 개수로 판단하지 않는다. 동결한 전체 목록, 출처가 있는 내용, 검토된 부착부, 실제 브라우저 경험, 누락의 공개가 함께 충족되어야 한다.
